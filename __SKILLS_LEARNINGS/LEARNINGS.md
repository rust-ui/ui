## Confirmed

- 2026-09-10 [rust] avoid hand-written `match self { Enum::Variant => "Variant", ... }` for enum-to-string, do derive `strum::IntoStaticStr` / `strum::AsRefStr` (+ `#[strum(serialize_all=...)]` or per-variant `#[strum(to_string=...)]`) and call `.into()` / `.as_ref()`, because single source of truth, no variant/string drift, less boilerplate. Keep a manual match only when one enum needs several different string projections (e.g. `dot_color()` + `text_color()` + `label()`) or computed values; then still use `Self::Variant` arms (clippy::use_self). Precedent: src/markdown/highlight_language.rs, use_workflow.rs EdgeStyle.

## Inbox

- 2026-09-16 [dioxus/editor] avoid generic `dioxus-editor-{n}` DOM id prefix for the rich text editor, do use `rust-ui-editor-{n}`, because project-branded id prefix preferred over framework-generic one.
- 2026-09-16 [dioxus/deps] avoid bumping the root `Cargo.toml` `dioxus`/`dioxus-html` pin off `=0.7.9`, do keep it pinned even though the locally installed `dx` CLI is 0.7.10 (version-mismatch warning at `dx serve` startup is expected, not a bug to fix), because dioxus 0.7.10 requires dioxus-desktop 0.7.10 which is unpublished on crates.io (desktop skipped straight to 0.8.0-alpha) and the desktop target hasn't upgraded yet.
- 2026-09-16 [testing] avoid Playwright CLI/spec fallback for manual UI validation, do use Playwright MCP mandatorily and save screenshots under `.playwright-mcp/`, because visual interaction checks must happen through the MCP workflow.
- 2026-09-10 [dioxus] avoid `dx fmt` in this workspace, do use `cargo fmt` only (rustfmt leaves rsx! bodies alone), because `dx fmt` reformats the entire workspace (300+ files, incl. leptos-ui submodule) and corrupts `app_crates/registry/src/blocks/sidenav_common.rs` (unexpected closing delimiter at :260) since it cannot round-trip that file's rsx.
- 2026-09-10 [dioxus] avoid raw `a { href: "/internal/path" }` for in-app navigation, do use `Link { to: Route::Variant { .. } }` (or `Link { to: format!(..) }`), because on `dx serve --platform ios` the webview loads from a non-http custom scheme so a real `<a>` nav triggers wry `Failed to open URL: not an http url`; `Link` intercepts the click in Rust and routes in-memory.
- 2026-09-11 [dioxus/ios] avoid calling `web_sys::window()`/`js_sys` (or any wasm-bindgen extern) unconditionally on a code path reachable from the iOS build, do gate it behind `#[cfg(target_arch = "wasm32")]` (whole `use_effect`/fn body, mirroring `use_pagination.rs`), because `dx serve --platform ios` compiles the crate natively for `aarch64-apple-ios(-sim)`, not wasm32, and wasm-bindgen's non-wasm32 stub panics unconditionally the instant the FFI call is made, even inside `if let Some(...)`/`.and_then(...)` guards on the `Option` it returns — the guard never gets a chance to run. Confirmed crash: `registry::hooks::use_table_of_contents`'s `use_effect` called `web_sys::window()` on mount, `EXC_CRASH`/`SIGABRT` navigating to any page using it. Audited and gated every other unconditional `web_sys::window()`/FFI call in `app_crates/registry/src/{hooks,demos}` the same way (a stored `web_sys::Element` *type* in a signal, never actually constructed on native, is safe and does not need gating — only the FFI call itself panics).
- 2026-09-14 [rust/clippy] avoid blindly applying `clippy::missing_const_for_fn` to a fn whose body is `#[cfg(target_arch = "wasm32")]`-gated, do add `#[allow(clippy::missing_const_for_fn)]` on that fn instead, because native-target clippy sees an empty (cfg'd-out) body and suggests `const fn`, but the real wasm32 body calls non-const `web_sys`/`wasm_bindgen` methods (`DomTokenList::add_1`, `Element::get_bounding_client_rect`, etc.) and drops non-const-droppable types (`Window`, `Document`, `DomRect`), so wasm32 CI build fails with E0015/E0493/E0658. Caused a fix/break ping-pong across 3 commits (5f128ae → 1deaa1f → 45c98c5) on `retrigger_page_fade` in src/utils/page_transition.rs before the `#[allow]` stuck.
- 2026-09-11 [dioxus/ios] avoid `__attribute__((constructor))` on a native ObjC `.m` patch file AND an explicit Rust `unsafe extern "C"` call to the same symbol, do pick exactly one invocation path (here: drop the constructor attribute, keep only the Rust call), because `dx` (unlike xcodegen/Tauri) links the crate as a Rust staticlib and prunes an archive member's `.o` unless something references its symbols — so the explicit Rust call is required just for linker inclusion — but keeping the constructor attribute too makes the patch run twice; for `WKWebView` method swizzling specifically, the second run captures the already-swizzled implementation as "original", causing infinite recursion the next time the swizzled method fires (`EXC_BAD_ACCESS`/stack overflow). Also: `static` (internal-linkage) C functions get their whole `.o` pruned by the linker if unreferenced from Rust — give them external linkage instead.
- 2026-09-15 [dioxus/ssr] avoid `document::Script { "literal js" }` (or any inline-children variant: plain `script { "..." }`, `script { dangerous_inner_html: "..." }`) to inject boot-time JS (e.g. a pre-paint dark-mode/splash-screen script), do put the JS in a real file under `public/` and load it with `document::Script { src: asset!("...") }` (pass small dynamic bits like an asset URL via a `"data-foo": ...` attribute, read with `document.currentScript.dataset.foo`), because `ServerDocument::create_script` (dioxus-server 0.7.9, `src/document.rs`) does forward `props.script_contents()` into the SSR'd `<script>` node in theory, but empirically the literal-children form never appears in curled SSR HTML under any of the 3 forms tried — only the `src` attribute reliably SSR-renders (confirmed: `<script src="/assets/foo-<hash>.js" data-logo="...">` shows up verbatim in the served HTML, matching how `document::Stylesheet`/existing `APEXCHARTS_JS`/`CHART_INIT_JS` already work). `document::Style { "literal css" }` is unaffected and does SSR correctly — this is a `Script`-specific gap. Also: Dioxus's `ServerDocument::render()` always emits `meta` then `link` then `script` groups in that fixed order regardless of rsx declaration order, so head-element ordering can't be controlled by where you place the component in `App()`'s rsx.
- 2026-09-16 [workflow/verification] avoid trusting `dx serve` log text or a DOM/JS assertion alone as proof a UI fix works, do always take a Playwright screenshot (`browser_take_screenshot`) of the actual rendered page before reporting a fix done, because during this session's editor toolbar-click fix, `browser_evaluate` checks (innerHTML, aria-pressed) all read as correct while the page was actually rendering completely unstyled (tailwind.css failed to resolve through the `dx`/`dioxus` version-skew asset manifest bug) — a screenshot caught it immediately, a DOM-only check would not have.
- 2026-09-16 [testing/playwright] avoid re-navigating an already-open Playwright MCP tab after a `dx serve` rebuild when it's stuck on the "One sec! We're building your app now." loading overlay, do `browser_close` the stale tab first then `browser_navigate` fresh, because `browser_navigate` on that stuck tab hangs and times out (`TimeoutError ... waiting until "domcontentloaded"`) even though `curl` confirms the server is up and serving the real page — the overlay's own reload-progress websocket had gone stale from an earlier server restart, not the app or the fix, so a plain screenshot of that tab misleadingly looks broken (grey "0%" progress page) when the underlying page/CSS is actually fine.
- 2026-09-22 [dioxus/js-interop] avoid `document.body.appendChild(node)` on a DOM node rendered by `rsx!` (reparenting a vdom-owned node from JS to escape a containing block, e.g. a header's `backdrop-blur`), do `document.createElement(...)` the node entirely in JS and never put it in `rsx!` at all, because Dioxus's vdom keeps its own node-id → DOM-node mapping from render time; reparenting via raw JS desyncs that mapping and the next diff/hydration pass (e.g. a page refresh) panics (`Cannot read properties of undefined (reading 'setAttribute')`, `RefCell already borrowed`, `RuntimeError: unreachable`). A JS-only-created node is never vdom-tracked so no desync is possible. Confirmed root cause of a hydration panic on `/docs/components/*` refresh in `app_crates/registry/src/ui/navigation_menu.rs`'s nav-dropdown overlay.
- 2026-09-22 [css] avoid assuming a sticky/fixed header only affects layout, do check it for `backdrop-blur`/`filter`/`transform`/`will-change` before adding any `position: fixed` descendant meant to span the full viewport (overlays, dropdown panels), because those properties create a new containing block, trapping the fixed descendant inside the header's small box instead of the true viewport — same root cause hit twice this project on `app_crates/registry/src/ui/navigation_menu.rs` (dropdown positioning, then the dim/blur overlay), both times traced to `header_docs.rs`'s `backdrop-blur` class. The working escape pattern is `command.rs`'s backdrop/dialog: mount as a JS-created (or component-tree) sibling outside the blurred ancestor entirely, not a CSS `z-index` bump.
